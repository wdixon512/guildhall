## Critical issues and resolutions proposed

1. **Phase boundary conflicts.** Sections 15 and 16 describe different first assignments. Phase 0 ends with a status screen, local authenticated host connectivity, a verified SQL migration pipeline, and Ollama model listing. Agent registry, conversations, token streaming, cancellation of inference, and exports belong to later phases.
2. **Local authentication has no bootstrap design.** Loopback and CORS alone do not establish caller identity. Propose a random per-development-session bearer token generated by the launcher, passed to the host through its process environment and to a narrow Tauri command through the desktop process environment. React holds it in memory only. Never put it in URLs, Vite build variables, browser storage, files, or logs. Reject missing/invalid tokens; restrict allowed origins and Host values. This mitigates unrelated web origins, not malicious software running as the same OS user. Packaged launch/bootstrap needs its own later decision.
3. **SQL Server changes the operational baseline.** A running local SQL service is now required for persisted operation. Target the existing default instance (`localhost`, service `MSSQLSERVER`) and propose a new `GuildhallDev` database; do not reuse business databases. Use a restricted SQL login for runtime and the existing Windows identity for explicit migrations. Keep encryption enabled, with the accepted certificate-validation exception limited to this local development instance. Review actual grants and credential storage before provisioning. No automatic service installation, TCP enablement, or firewall changes. Database readiness is separate from host liveness; the UI can diagnose SQL failure without losing host connectivity.
4. **Data ownership needs a recovery definition.** Versioned schemas plus native backup/restore and documented logical exports are required for long-term ownership. Phase 0 proves migration persistence, repeatability, and failure behavior; it contains no conversations to export. Define a backup/restore procedure before meaningful Phase 1 data accumulates. Database backups are sensitive and do not include OS-protected secrets.
5. **Contracts are too broad for the first slice.** Keep provider-specific discovery JSON behind a host adapter. Publish only health, readiness, and normalized model discovery DTOs now. Do not create a universal agent protocol or capability matrix before inference exists. Later provider-neutral messages must support ordered text/tool blocks and provider provenance without silently losing data on provider switching.
6. **Event durability is underspecified.** Before Phase 1, decide which events are durable, whether deltas are persisted or coalesced, replay ordering, interrupted-run recovery, cancellation ownership, and context limits. This is a future design gate, not permission to build an event bus in Phase 0.
7. **Worktrees are not execution sandboxes.** They isolate Git changes but cannot restrict filesystem, network, or process permissions. Phase 4 needs a real enforcement design for running commands. MCP integration itself does not authorize tool use. Phase 0 exposes no execution tools.
8. **Lifecycle ownership is unspecified.** During Phase 0 a PowerShell development launcher owns the host and desktop child processes. It checks port availability, waits for authenticated health, reports startup failure, and stops only its own children. It neither kills processes occupying ports nor manages SQL/Ollama services. Packaging and independent background execution stay deferred.

## Phase 0 contracts proposed

- `GET /health`: authenticated liveness; 200 with `status: "ok"` and API version even when SQL/Ollama are down. No machine paths, tokens, connection strings, or detailed exception text.
- `GET /ready`: authenticated SQL connectivity and expected schema-version check; 200 when ready, 503 with a bounded stable reason code when unavailable or migration is required. Never runs migrations. Ollama does not gate host/database readiness.
- `GET /models`: authenticated discovery through Ollama's local `GET /api/tags`; normalized `providerId`, `status`, and `models` containing `id` and `displayName`. Status distinguishes `available`, `no_models`, `unavailable`, and `invalid_response`. No prompts, generation, downloads, or model loading.
- Discovery has a short finite timeout, cancellation, bounded response size, no redirects, and sanitized errors. Its configured endpoint is loopback-only in Phase 0. Model listing proves installation/discovery, not GPU fit, inference capability, or tool reliability.
- Proposed development API is `http://127.0.0.1:43120`; Vite also binds loopback. Allow only the actual desktop origin and the exact configured development origin. Restrict CSP to required local endpoints and assets; no remote content navigation or broad filesystem/shell plugin capability.
- SQL Server is reached only by the host. Runtime credentials use OS-protected local storage and enter only the host process configuration, never `VITE_*` or desktop environments. SQL connections remain encrypted. The user approved a certificate-validation exception for the selected local development instance only; remote connections require certificate validation.
- The initial migration creates only an application metadata record identifying installation/schema bootstrap. No speculative agent/chat/run/tool tables. Use a separate explicit migration command against an already approved dedicated database, never production startup auto-migration.
